# Stateless Pi-style bash operation worker

Implements `tool-pi-bash/bash/v1` using the execution gateway's `execution.run` operation. It owns request translation, dedicated-user credentials, Pi output formatting and synchronous completion admission into the session DO. The gateway owns durable jobs, idempotency, results and callback retries.

**Deployed on 2026-09-20.** This breaks the previous D1/Queue-based worker protocol. Live bindings and source/configurations target `minimal-bash/v7`. V6 work was drained before switching; see the [v7 rollout](../../DEPLOYMENT.md). The old Queue consumer is detached, D1/Queue bindings and cron are removed, and the dedicated execution user uses v3 callbacks. Old databases, Queues and older code/data are retained; secrets and callback URLs are unchanged. See the [deployment guide](../../DEPLOYMENT.md).

## Submission

The private `PiBash.submit` binding accepts a structured object:

```ts
{
  destination: { routeKey, sessionId },
  submission: {
    operationId, submissionId,
    request: {
      provider: "tool-pi-bash", type: "bash", version: "v1",
      input: { machineId, cwd, command, timeout? }
    }
  }
}
```

The harness supplies machine/cwd; the model supplies only command and optional timeout in seconds. Paths must be absolute. Empty commands are valid. Extra fields, NUL commands, model-supplied credentials, callback/routing context and shell/environment overrides are rejected. No default timeout is injected. Fractional milliseconds are truncated with a minimum of 1 ms; the maximum timer is 2,147,483,647 ms. The shared operation input limit remains 8 MiB, subject to the gateway's envelope/frame limits.

After validation and checking the allowlisted return route, the worker calls authenticated `POST /v1/jobs`:

```ts
{
  machineId,
  idempotencyKey: "pi-bash-v1:" + sha256(submissionId),
  clientContext: {
    receiver: "tool-pi-bash-v1", routeKey, sessionId,
    operationId, submissionId, machineId,
    timeoutSeconds: timeout ?? null
  },
  request: {
    operation: "execution.run",
    params: {
      run_id: idempotencyKey,
      cwd,
      max_output_bytes: 65536,
      command: {
        type: "shell", script: command,
        shell: { executable: "bash", kind: "bash" }, login: false
      },
      timeout_ms // only when timeout was supplied
    }
  }
}
```

Context is generated by the trusted adapter, not accepted as a tool argument. The gateway persists it and includes it in request-conflict detection. Every replay uses the same job identity and context. The worker stores neither the request nor a hash/reservation locally.

A normal reply is `{ result: { status: "accepted", jobId } }`. If POST finds an already-terminal job, the worker fetches its detail, validates job/machine/key/context/status and returns `{ result: { status: "completed", jobId, outcome } }`. This replay path is the **only** result GET. A failed detail read throws; it cannot become a definitive submission rejection. The runtime retains its source and retries the same identity.

Known pre-acceptance validation/machine-disabled/not-found errors return `rejected`. Authentication, offline/capacity errors, conflicts, malformed responses and ambiguous transport failures throw. There is no local acceptance/rejection cache, polling or private diagnostic `get`.

Normal submission: **zero D1 calls, zero Queue messages, one gateway POST**.

## Completion delivery

The gateway sends a signed **webhook payload version 3** to the common [execution callback router](../execution-gateway-callback-workers/README.md). The router validates the envelope/signature, selects an allowlisted receiver and forwards the structured event to `PiBashCallbacks.acceptGatewayEvent`.

The callback-only entrypoint:

1. Validates v3 plus the exact bash context shape.
2. Checks the signed machine ID and derived idempotency key.
3. Selects the allowlisted session namespace.
4. Normalizes the inline result, validating protocol version, job/request ID, generation and run identity.
5. Calls the DO's structured `acceptCompletion` action.
6. Returns `{ receipt: { status: "accepted", eventId, jobId, clientContext } }` only after the matching durable DO receipt.

There is **no gateway GET**, D1 access, Queue, `waitUntil` forwarding or early local acknowledgement on this path. Early callbacks use the runtime's existing prepared-plan admission checks and can be admitted before POST returns; they cannot overtake the source input. The old early-callback Queue handoff is removed.

The router waits for this receipt before returning HTTP 204. Admission failure or a lost/invalid receipt propagates as 503; the gateway redelivers. The runtime deduplicates by operation/outcome, including after payload cleanup or activation loss. Conflicting outcomes do not overwrite admitted results. Consumed duplicates reuse the optimized single-read admission path in v6.

## Tool results

`formatRun` retains the existing Pi behavior:

- Decode stdout/stderr in returned capture order, including UTF-8 chunk/tail boundaries.
- Keep the last 2,000 lines or 50 KiB, whichever binds first, from the gateway's 64 KiB preview.
- Preserve honest truncation/incomplete-capture notices.
- Include the full-output machine path, artifact ID, size, digest and expiry. The full file stays on the execution host.

```ts
{
  status: "succeeded",
  result: {
    content: [{ type: "text", text: "formatted output" }],
    isError: false,
    details: {
      gatewayJobId, machineId, runId, executionHandle,
      reason, exitCode, signal, timedOut,
      fullOutputPath, outputFile, truncation
    }
  }
}
```

Known nonzero exit, timeout, termination and launch failure are completed tool results with `isError: true`; the model can respond to them. Gateway/protocol errors are failed operations. Gateway `unknown` or execution `lost` becomes `BASH_EXECUTION_UNKNOWN`: execution may have occurred and must not be automatically repeated. Minimal-bash fails the run on that uncertainty.

Malformed/miscorrelated terminal responses are not acknowledged as successful delivery and do not authorize replacement jobs.

## Deadlines and recovery ownership

The complete submit/replay path has an eight-second budget, with individual gateway requests capped at seven seconds. The router has an eight-second end-to-end callback budget including body reading, signature verification, tool RPC and DO admission; the bash callback entrypoint also bounds its own work at eight seconds. Gateway HTTP/body reads support abort; RPC cannot be cancelled, so a timed-out call may still admit and later redelivery must deduplicate.

After acceptance the gateway is the **only delivery-recovery owner**. Its current implementation has eight attempts within a maximum 24-hour retry window, a ten-second callback HTTP timeout, failed-delivery inspection and manual redelivery. Attempts can exhaust before 24 hours. Without operator redelivery a session may remain waiting. Retain gateway idempotency/results and credentials for the recovery horizon; deleting them can break replay.

Job-detail transport remains bounded at 18 MiB because it can contain retained request plus response. The router's v3 body cap is also 18 MiB. Normal bash results carry only the bounded output preview. Oversized transport or invalid results do not silently become successful tool results. No R2 reference or full-output upload is added.

## Bindings and security

- `EXECUTION_GATEWAY_URL`: HTTPS origin.
- `EXECUTION_GATEWAY_API_KEY`: dedicated gateway user's key.
- `SESSION_ROUTES`: allowlisted route key → namespace binding.
- `MINIMAL_BASH_SESSIONS` binding for `minimal-bash-v7` in source/configurations and live deployment.

There are no `BASH_DB` or `COMPLETIONS` bindings and no scheduled/queue handler. The cron list is explicitly empty. Signature secrets and the public callback route belong only to the shared router. The only public handler here is health; submission and callbacks are private service bindings. Bind the callback entrypoint only to trusted routers; it cannot submit commands. Gateway machine ownership is not a per-session sandbox, and cwd is not a filesystem security boundary.

## Deployment and breaking rollout

The original stateless rollout below is historical. For the v7 storage rollout, follow the [v7 host rollout](../harness-minimal-bash/README.md#setup-and-rollout); no gateway/router changes are needed. When adopting the stateless protocol from an older installation, coordinate with the [router rollout](../execution-gateway-callback-workers/README.md#deployment-and-breaking-rollout):

1. Pause new inputs/resume traffic and drain all old operations, source retries, callbacks and local Queue work using the old deployed code. Old `{ receiver, reference }` jobs cannot be handled by these adapters.
2. Verify the upstream gateway supports v3 and matching replay/context semantics. The user reports that support deployed; that does not prove the dedicated user's payload setting has been switched.
3. Detach both old Queue consumers after draining. Deploy coordinated stateless bash/router code, preserving URL/secrets. Verify deployed bindings, consumer registrations and cron lists—not just source code.
4. Establish the v6 namespace and switch LLM/bash/API bindings as documented by the host. Do not rebuild existing immutable v5 objects against changed workspace packages.
5. Set the dedicated execution user to `webhookPayloadVersion: 3` while traffic remains paused, preserving the common callback URL. The old router rejects v3 and this router rejects v1/v2.
6. Test real LLM → bash → LLM, duplicate callbacks, gateway delivery status, transcript and same-session follow-up before restoring traffic.

Do not delete old remote databases/Queues as part of deployment. They remain available for separately approved cleanup. Once new-context jobs exist, rollback to the old stateful code is not an automatic safe recovery path. Drain or preserve a receiver capable of their contract first.

## Checks

`pnpm --filter @managed-agents/tool-pi-bash-workers check` runs typechecks, Pi-formatting tests, real workerd RPC/SQLite integration with production router+tool code and no adapter D1/Queue bindings, and a dry-run build. Coverage includes early/concurrent/duplicate callbacks, signed result tampering, terminal replay, command/gateway failures, lost receipts, restart and deadline expiry. Full-stack harness tests assert zero LLM and execution result GETs on the callback path. No live command, deployment or gateway-user mutation is performed by checks.

## Execution protocol compatibility

Callbacks and terminal job replay accept numeric execution protocol versions **4
and 5**, preserving retained v4 jobs during the v5 rollout. Other versions and
malformed version fields are rejected; job, runtime generation and tool-specific
receipt validation still apply. This is independent of the signed webhook's
`schemaVersion: 3`. Requests use the existing gateway operation envelope, which
leaves native protocol-version selection to the gateway.
